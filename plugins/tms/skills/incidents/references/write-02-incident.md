# 신규 장애 등록 진행 방법

[쓰기 공통 절차](write-01-common.md)를 함께 따른다. 현재 등록 도구는 `create_incident`다.
필드명·필수값·허용 enum은 실행 시 도구 스키마를 확인한다. 읽기 필터의 한글 라벨 허용을
쓰기 입력에도 그대로 적용할 수 있다고 가정하지 않는다.

## 등록 의도와 대상 확정

"서버 다운 장애를 등록해줘"는 신규 장애 등록이다. "기존 장애에 출동 내용을 추가해줘"는
대응 기록 추가이므로 신규 장애로 대신 등록하지 않고 [대응·조치 등록](write-03-history.md)을 따른다.

대상(`targets`)은 내부 ID가 아니라 조회로 확인한 **공개 식별자**로 지정한다. 서버가 식별자를
내부 ID로 바꾸고, 터널·장비·지사만 주면 상위 본부·지사를 자동으로 채운다.

| 대상 | 입력 | 값을 얻는 곳 |
|---|---|---|
| 터널 | `{"tunnelCode": "030100"}` | 카탈로그 캐시의 `코드`, `search_tunnels` |
| 장비 | `{"deviceId": "001004DM3830"}` | `search_equipment` 상세의 `장치ID` |
| 지사 | `{"branchName": "당진지사"}` | 카탈로그 캐시의 지사 키 (터널 없는 지사도 포함) |
| 본부 | `{"divisionName": "충북본부"}` | 카탈로그 캐시의 본부 키 |
| 시스템 | `{"system": {"category": "ATMS", "subcategory": "통합 웹"}}` | 카탈로그 캐시의 `시스템분류` |

- 약식 이름("피반령", "문의2")은 [catalog 스킬](../../catalog/SKILL.md)로 정식명·코드를 확정한다.
  동명 터널이 있으면 임의로 고르지 않고 필요한 구분(본부·지사)만 질문한다.
- 시스템 대상에는 적용 본부 `divisionName`만 함께 줄 수 있다. 본부를 생략하면 전체 본부다.
- 일반적인 터널 장애는 `tunnelCode` 하나로 충분하다. 상위 본부·지사를 함께 주면 실제 소속과
  다를 때 거부되므로, 확인하지 않은 상위 값을 덧붙이지 않는다.
- 식별자를 찾지 못하면 서버가 `incident_target_not_found`로 등록 없이 거부하고 틀린 위치를
  알려준다(시스템 분류는 가능한 값도 준다). 이 경우 등록이 일어나지 않았으므로 식별자를 고쳐
  **같은 UUID**로 다시 보내도 된다. 내부 ID·숫자를 만들어 넣지 않는다.

## 내용 준비와 전송

사용자가 제공한 현상·요청 내용을 바탕으로 분류와 메모를 작성한다. "서버 교체 필요"를
"서버 교체 완료"로 바꾸지 않는다. 명확히 요청하고 충분한 정보를 준 등록을 매번 재승인받을
필요는 없으며, 대상·내용이 불명확한 경우에만 필요한 질문을 한다.

사용자가 접수 시각을 지정했다면 시간대를 확인해 KST 입력으로 전달한다. 현재 접수 시각을
뜻하고 별도 시각을 지정하지 않았다면 선택 입력을 생략해 서버 시각을 사용한다.
시계 확인 없이 현재 시각을 추측하거나 UTC 시각에 KST 표기만 붙이지 않는다.

공통 절차로 UUID·입력을 기록한 뒤 도구를 호출한다. 접수자·작성자를 지정하려고 인증 정보나
지원하지 않는 필드를 추가하지 않는다. 장애코드도 직접 만들지 않고 서버의 등록 결과를 사용한다.

## 완료 안내와 조회 확인

성공 결과를 작업 기록에 저장하고 장애코드·대상·접수일시·상태·메모 요약을 안내한다.
사용자가 반영 확인을 원하면 반환된 전체 장애코드로 조회하고 코드가 정확히 일치하는 결과를 확인한다.
조회 결과가 바로 보이지 않아도 등록을 새 UUID로 다시 실행하지 않는다.
