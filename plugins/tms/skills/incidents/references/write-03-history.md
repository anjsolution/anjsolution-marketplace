# 기존 장애에 대응 기록·조치 결과 등록

[쓰기 공통 절차](write-01-common.md)를 함께 따른다. 도구는 `add_incident_responses`(대응 기록)와
`add_incident_resolution`(조치 결과)다. 필드명·허용값·건수 제한은 실행 시 도구 스키마를 확인한다.
두 도구가 현재 연결에 없으면 대응·조치 등록을 지원하지 않는 연결로 보고 사용자에게 알린다.

## 대상 장애 확정

"대관령1터널 장애에 출동 내용 추가해줘"처럼 기존 장애를 가리키면 먼저 `search_incidents`로 찾는다.
두 도구는 조회 응답의 **장애코드 전체**로 대상을 받는다. 장애코드를 만들거나 일부만 쓰지 않는다.
후보가 여러 건이면 접수일시·메모·상태로 구분해 사용자에게 확인한다.
대응·조치를 추가하려는 것을 신규 장애 등록으로 대신하지 않는다.

## 대응 기록 추가

- 등록 전에 `include_history=true`로 기존 대응이력을 확인한다. 같은 일시·내용이 이미 있으면 다시
  보내지 않는다. 대응 기록에는 건별 원본 키가 없어 서버가 내용 중복을 막아 주지 않는다.
- 한 번의 요청에 여러 건을 함께 보낼 수 있다. 한 요청의 목록은 모두 성공하거나 모두 실패한다.
  건수 제한을 넘으면 요청을 나누고 요청마다 별도 UUID를 쓴다.
- 대응일시는 +09:00 KST로 쓴다. 사용자가 시각을 주지 않았다면 추측하지 않고 묻거나, 현재 시각을
  뜻하는 경우에만 생략한다.
- 대응자 이름을 생략하면 현재 사용자로 기록된다. 이름이 등록 사용자와 일치하면 그 계정에 연결된다.
- 대응 기록 추가는 장애 상태를 바꾸지 않는다.

## 조치 결과 등록

- 조치 결과는 장애당 **최초 1회만** 등록되고 상태가 RESOLVED로 바뀐다. 이미 조치가 있으면 거부된다.
  MCP에는 조치 수정 도구가 없으므로 수정은 웹 화면에서 해야 한다고 안내한다.
- 되돌릴 수 없으므로 전송 전에 대상·방법·접근·유형·원인·조치 내용을 사용자에게 한 번 보여 준다.
  사용자가 내용을 모두 명시해 요청했다면 그대로 진행한다.
- 조치 대상·방법·접근·유형은 조치코드 4자리(예: SCCH = 서버·교체·현장·하드웨어)와 대응한다.
  사용자가 준 코드 글자가 도구 허용값에 없으면 비슷한 값으로 바꾸지 말고 그 사실을 알린다.
  예를 들어 방법 자리 O(Other, 운영미숙 포함)는 서버 지원 여부를 스키마에서 확인한다.
- 원인은 `cause`, 조치 내용은 `memo`, 비고는 `remarks`에 나눠 담는다. 한 칸에 합치지 않는다.
- 조치자 이름 규칙은 대응자와 같다.

## 결과 안내

대응은 등록된 건수와 일시별 요약을, 조치는 조치코드·조치일시·상태를 안내한다. 반영 확인이 필요하면
장애코드로 다시 조회해 대응이력과 조치결과를 보여 준다. 결과가 불명확했다가 재시도로 성공한 경우에도
중복이 없는지 조회로 확인했다고 밝힌다.
