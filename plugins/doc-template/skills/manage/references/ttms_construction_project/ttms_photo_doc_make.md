# 현장 사진으로 사진대지 만들기 (ttms_construction_project/ttms_photo_doc_make)

> **임시 위치 — TTMS 구축 전용 플러그인으로 이전 예정.** 이 폴더의 `README.md` 참고.

## 언제 쓰나
- 현장에서 찍은 사진 폴더를 받아 입고·납품·설치 사진대지를 만들 때
- 사용자가 사진마다 설명·순서를 주지 않았을 때 — 사진의 촬영 시각·위치와 내용으로 직접 묶고 설명을 단다

사진은 읽기만 한다. 양식 원본도 고치지 않는다.

**이 문서만으로 바로 시작한다.** `ttms_photo_doc_types`(필요한 사진 목록)·`ttms_photo_doc_location_data`(위치·방문 정리)를 먼저 읽거나 실행할 필요는 없다. 아래 절차 중 필요한 단계에서만 그 문서를 참고한다 — 예: 필수 사진 확인이 필요할 때 types, 방문이 여러 곳일 때 location_data. 사용자가 사진·순서·설명을 이미 주었다면 해당 루틴은 건너뛰고 바로 채우기로 간다.

## 쓰는 기능
| 단계 | 기능 | 상태 |
|---|---|---|
| 사진 분석 | `analyze_image` (`scripts/analyze-image.mjs -r --json`) | 제공 |
| 방문(시간대·위치)별 묶기 | `ttms_photo_doc_location_data` (`photo-visits.mjs --json`) | 제공 |
| 사진 설명 만들기 | 사진을 직접 보고 설명 작성 — 사진이 많으면 지금 환경에서 쓸 수 있는 가장 저렴한 모델의 서브에이전트에 맡긴다 | 제공 (전용 에이전트는 예정) |
| 양식 채우기·페이지 늘리기 | `hwpx` 스킬 (`pages` → `fill`/`export`) | 제공 |
| 설치 장소(관리동·지사·본부·○○청 서버실 등) 등록·위치 검토·좌표/주소 채우기 | — | **제공 예정** |

## 절차

서로 기다릴 필요가 없는 일은 동시에 진행한다. 사용자에게 묻는 것은 한 번에 모아서 묻는다.

```
1 사진 폴더 받기 (이것만 있으면 시작)
   └─ 2 동시에 시작 ─┬─ A. 분석 → 묶기 → (장소 질문 준비)        [사진 메타데이터 루틴]
                    ├─ B. 사진 설명 만들기 (서브에이전트, 백그라운드) [사진 내용 루틴]
                    ├─ C. 양식 확인·값 JSON 뼈대 만들기              [양식 루틴]
                    └─ D. 설치 장소 위치 정리 — 제공 예정 안내만
3 질문 한 번에: 종류·이중화·공사명 등 빈 값(C) + 장소(A) + 확인 필요한 설명·빠진 필수 사진(B+C)
4 최종 확인: 페이지별 사진 순서·설명 목록
5 채우기: C 의 뼈대에 A 의 순서·장소, B 의 설명을 넣어 hwpx 스킬 fill/export
```

### 1. 사진 폴더 받기
사진 폴더만 있으면 바로 2단계를 시작한다. 종류(입고/납품)·공사명·이중화 여부 같은 정보는 따로 먼저 묻지 않는다 — 요청이나 대화 맥락에 있으면 쓰고, 없으면 3단계 질문에 함께 넣는다.
카카오톡 압축본(촬영 시각·GPS 없음)이어도 멈추지 않는다. 어차피 B 에서 사진 내용을 분석하므로 그대로 진행하고, 부족한 정보는 3단계에서 묻는다.

### 2. 동시에 시작 (A·B·C·D)

**A. 사진 메타데이터 루틴 — 분석 → 묶기 → 장소 질문 준비** (이어지는 한 흐름)
- `analyze-image.mjs <폴더> -r --json` — 장수, 촬영 시각·GPS 유무, 크기·용량. 5MB 넘는 사진이 많으면 문서가 커진다고 알린다(압축은 이후 manage 기능 예정).
- 묶기:
  - GPS·시각이 있으면 `photo-visits.mjs <폴더> -r --json` 의 방문(시간대 + 위치)으로 묶는다. 사용자가 사진 정보를 주지 않아도 이 JSON 으로 직접 묶는다.
  - 시각만 있으면 촬영 시각순으로 놓고 시간 간격으로 나눈다.
  - 둘 다 없으면 파일 순서대로 두고 순서를 확인 질문에 넣는다.
- 방문이 여러 곳이면 `ttms_photo_doc_location_data` 절차의 장소 질문("○월 ○일 ○시, 사진 ○장 — 어느 설치 장소(관리동·지사·본부·○○청 서버실 등)인가요?")을 준비한다. 주소 변환이 필요하면 동의 질문도 함께 준비한다.
- 두 스크립트 모두 1초 안에 끝나므로 서브에이전트에 맡기지 않고 바로 실행한다.

**B. 사진 내용 루틴 — 설명 만들기** (A 와 무관, 사진만 있으면 된다)
- 사진 설명 칸(예: `내용-1`)이 있고 사용자가 설명을 주지 않았을 때만 한다.
- **지금 환경에서 쓸 수 있는 가장 저렴한 모델**의 서브에이전트를 **백그라운드로** 띄워 (Claude Code 라면 Haiku — 이미지를 볼 수 있는 모델이어야 한다) 사진 목록을 넘기고 `{파일, 설명(15자 안팎 명사형), 확신도, 중복 의심}` JSON 을 받는다. 결과는 파일 이름 기준이라 A 의 묶음 순서와 나중에 합치면 된다.
- 서브에이전트나 모델 선택을 쓸 수 없는 환경(예: Codex 등)이면 현재 모델이 직접 사진을 보고 같은 형식으로 만든다. 사진이 많으면 몇 장씩 나눠 본다.
- 설명 이름은 `ttms_photo_doc_types.md` 의 사진 항목 이름을 기준으로 한다.
- 사진 속 글자(서버 정보 종이, 박스·서버 라벨의 Master/Main·Slave 표기, 시리얼 번호)를 읽어 **어느 서버 사진인지** 함께 적게 한다. 이중화 여부와 사진 순서(Master 전부 → Slave 전부)를 정하는 근거가 된다. 글자로 구분되지 않는 서버 사진은 `구분 불가` 로 표시해 3단계 질문에 넣는다.
- 랙·박스·동작 확인 화면처럼 **사진 종류가 드러나는 사진**이 있으면 입고/납품 종류를 추정하는 근거로 쓴다(3단계에서 기본값으로 제안).
- 확신도가 낮거나 중복 의심인 사진, 라벨에 다른 사업명·터널명이 보이는 사진을 확인 질문에 넣는다.

**C. 양식 루틴 — 양식 확인·값 JSON 뼈대** (사진과 무관)
- 사진대지 양식 후보를 준비한다. 종류·이중화를 아직 모르면 네 양식(입고/납품 × 단일/`_dual`)의 토큰을 미리 확인해 두고, 3단계 답을 받은 뒤 하나로 정한다(사진 페이지 토큰은 넷이 같고, 표지 서버 표만 단일/이중화가 다르다). 플러그인에 들어 있는 양식: `templates/ttms_construction_project/` — 입고 `server_receiving_photo_sheet.hwpx`, 납품 `server_delivery_photo_sheet.hwpx`, 이중화면 각각 `_dual` 판. 사용자가 다른 양식 파일을 주면 그것을 쓴다.
- `hwpx` 스킬의 `pages <서식>` 으로 반복할 사진 페이지 번호, 페이지당 사진 칸 수(예: 2장), 공통 키(공사명·위치·날짜 등)를 확인한다.
- **이중화 여부**(서버 2대인지)는 맥락에 없으면 3단계 질문에 넣는다. B 가 Master/Slave 사진을 찾았으면 "이중화로 보입니다"를 기본값으로 제안한다. 이중화면 `_dual` 양식을 쓰고 표지 서버 표에 Master·Slave 두 대(`모델명-1`, `S/N-1`, `모델명-2`, `S/N-2`)를 채우며, 사진은 Master 세트 전부 → Slave 세트 전부 순서로 놓는다(`ttms_photo_doc_types` 의 이중화 터널 항목).
- 양식의 `{{키}}` 중 맥락으로 아는 값(공사명 등)은 채우고, 모르는 것은 3단계 질문에 넣는다. 날짜를 촬영 시각으로 채우려면 그것도 질문에 넣는다. 방문 날짜가 여러 날이면 날짜를 페이지별로 넣을지 묻는다.
- 결과 저장 위치: 맥락에 없으면 3단계에서 묻는다. 기본값은 사진 폴더의 상위 폴더이며, **사진 원본 폴더 안에는 저장하지 않는다**.

**D. 설치 장소 위치 정리 — 제공 예정** (위 셋과 별개)
아직 없는 기능이다. 요청이 오면 "제공 예정" 이라고 안내하고, 지금은 A 의 방문 → 장소 표를 넘겨준다.
- 설치 장소(터널 관리동, 지사·본부·○○청 서버실 등)가 등록돼 있지 않으면 등록
- 등록돼 있으면 위치 정보가 저장돼 있는지 확인하고, 사진 위치와 맞는지 검토해 수정 제안
- 비어 있는 주소·위도·경도 채우기

### 3. 질문 한 번에
먼저 **필수 사진 확인**을 한다 — B 의 설명과 정해진 종류로 `ttms_photo_doc_types.md` 의 필수 사진(예: 납품의 랙 설치 전·후 전면·후면 4장, H/W·S/W 정상 실행)이 다 있는지 보고 빠진 것을 질문에 넣는다(사진 내용을 봐야 알 수 있으므로 B 결과가 필요하다).

메타데이터(촬영 시각·GPS)가 없는 사진이 많으면 질문 앞에 한 줄로 안내한다: "사진에 촬영 날짜·위치 정보가 없어 사진 내용으로 정리했습니다. 날짜·장소를 알려 주시거나, 사진을 직접 나눠 주시거나(예: 폴더별), 원본 사진(카카오톡 '원본으로 보내기'·휴대폰에서 직접 복사)을 주시면 더 정확해집니다."

서버 구분이 안 되는 사진이 있으면 파일 이름과 함께 묻는다: "Master/Slave 구분이 어려운 사진입니다 — ○○.jpg, △△.jpg. 어느 서버인지 알려 주세요(또는 서버 정보 종이가 보이는 사진을 추가해 주세요)."

A·B·C 에서 모은 질문을 한 메시지로 묻는다: 종류(입고/납품)·이중화·공사명 등 빈 값(추정한 기본값과 함께), 방문별 장소, 확인이 필요한 사진 설명·중복·서버 구분, 빠진 필수 사진, 사진 순서(시각이 없을 때), 날짜 기준, 방문이 바뀔 때 새 페이지에서 시작할지, 결과 저장 위치, 주소 변환 동의(필요할 때).
B 가 아직 끝나지 않았으면 A·C 질문을 먼저 묻고, B 결과는 도착하는 대로 이어서 확인한다.

### 4. 최종 확인
답을 반영해 양식을 하나로 정하고, 페이지별 사진 순서·설명 목록을 보여 준다(사진대지에 그대로 나가는 내용이다). 고칠 것이 없으면 5단계.

### 5. 채우기
C 의 뼈대에 A 의 순서·장소와 B 의 설명을 넣어 값 JSON 을 완성하고, `hwpx` 스킬로 `fill`(hwpx) 또는 `export`(PDF)를 실행한다. 결과 요약(값 없음·경고)을 전한다.

## 주의
- **위치(GPS)는 민감 정보다.** 사용자가 요청하지 않으면 좌표를 사진대지·값 JSON 에 넣지 않는다. 사진대지의 `위치` 칸에는 사용자가 확인한 장소 이름을 쓴다.
- 장소(설치 장소) 이름은 사용자가 답한 것만 쓴다. 좌표·주소만 보고 단정하지 않는다.
- 촬영 시각이 없는 사진의 날짜를 파일 이름으로 추측하지 않는다.
- 사진 순서·설명은 문서에 그대로 나가는 내용이다. 자동으로 정한 것은 넣기 전에 목록으로 보여 준다.
