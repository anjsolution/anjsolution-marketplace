# 현장 사진으로 사진대지 만들기 (ttms_construction_project/make_photo_sheet)

> **임시 위치 — TTMS 구축 전용 플러그인으로 이전 예정.** 이 폴더의 `README.md` 참고.

## 언제 쓰나
- 현장에서 찍은 사진 폴더를 받아 입고·납품·설치 사진대지를 만들 때
- 사용자가 사진마다 설명·순서를 주지 않았을 때 — 사진의 촬영 시각·위치와 내용으로 직접 묶고 설명을 단다

사진은 읽기만 한다. 양식 원본도 고치지 않는다.

## 쓰는 기능
| 단계 | 기능 | 상태 |
|---|---|---|
| 사진 분석 | `analyze_image` (`scripts/analyze-image.mjs -r --json`) | 제공 |
| 방문(시간대·위치)별 묶기 | `location_data_from_photos` (`photo-visits.mjs --json`) | 제공 |
| 사진 설명 만들기 | 사진을 직접 보고 설명 작성 — 사진이 많으면 지금 환경에서 쓸 수 있는 가장 저렴한 모델의 서브에이전트에 맡긴다 | 제공 (전용 에이전트는 예정) |
| 양식 채우기·페이지 늘리기 | `hwpx` 스킬 (`pages` → `fill`/`export`) | 제공 |
| 관리동 등록·위치 검토·좌표/주소 채우기 | — | **제공 예정** |

## 절차

서로 기다릴 필요가 없는 일은 동시에 진행한다. 사용자에게 묻는 것은 한 번에 모아서 묻는다.

```
1 사진 받기
   └─ 2 동시에 시작 ─┬─ A. 분석 → 묶기 → (장소 질문 준비)        [사진 메타데이터 루틴]
                    ├─ B. 사진 설명 만들기 (서브에이전트, 백그라운드) [사진 내용 루틴]
                    ├─ C. 양식 확인·값 JSON 뼈대 만들기              [양식 루틴]
                    └─ D. 관리동 위치 정리 — 제공 예정 안내만
3 질문 한 번에: 장소(A) + 확인 필요한 설명(B) + 빈 공통 값(C)
4 채우기: C 의 뼈대에 A 의 순서·장소, B 의 설명을 넣어 hwpx 스킬 fill/export
```

### 1. 사진 받기
폴더를 받는다. 카카오톡 압축본은 촬영 시각·GPS 가 없으니, 시간·장소별로 묶어야 하면 원본을 요청한다("원본으로 보내기" 또는 휴대폰에서 직접 복사).

### 2. 동시에 시작 (A·B·C·D)

**A. 사진 메타데이터 루틴 — 분석 → 묶기 → 장소 질문 준비** (이어지는 한 흐름)
- `analyze-image.mjs <폴더> -r --json` — 장수, 촬영 시각·GPS 유무, 크기·용량. 5MB 넘는 사진이 많으면 문서가 커진다고 알린다(압축은 이후 manage 기능 예정).
- 묶기:
  - GPS·시각이 있으면 `photo-visits.mjs <폴더> -r --json` 의 방문(시간대 + 위치)으로 묶는다. 사용자가 사진 정보를 주지 않아도 이 JSON 으로 직접 묶는다.
  - 시각만 있으면 촬영 시각순으로 놓고 시간 간격으로 나눈다.
  - 둘 다 없으면 파일 순서대로 두고 순서를 확인 질문에 넣는다.
- 방문이 여러 곳이면 `location_data_from_photos` 절차의 장소 질문("○월 ○일 ○시, 사진 ○장 — 어느 관리동(장소)인가요?")을 준비한다. 주소 변환이 필요하면 동의 질문도 함께 준비한다.
- 두 스크립트 모두 1초 안에 끝나므로 서브에이전트에 맡기지 않고 바로 실행한다.

**B. 사진 내용 루틴 — 설명 만들기** (A 와 무관, 사진만 있으면 된다)
- 사진 설명 칸(예: `내용-1`)이 있고 사용자가 설명을 주지 않았을 때만 한다.
- **지금 환경에서 쓸 수 있는 가장 저렴한 모델**의 서브에이전트를 **백그라운드로** 띄워 (Claude Code 라면 Haiku — 이미지를 볼 수 있는 모델이어야 한다) 사진 목록을 넘기고 `{파일, 설명(15자 안팎 명사형), 확신도, 중복 의심}` JSON 을 받는다. 결과는 파일 이름 기준이라 A 의 묶음 순서와 나중에 합치면 된다.
- 서브에이전트나 모델 선택을 쓸 수 없는 환경(예: Codex 등)이면 현재 모델이 직접 사진을 보고 같은 형식으로 만든다. 사진이 많으면 몇 장씩 나눠 본다.
- 설명 이름은 `photo_sheet_types.md` 의 사진 항목 이름을 기준으로 한다.
- 확신도가 낮거나 중복 의심인 사진, 라벨에 다른 사업명·터널명이 보이는 사진을 확인 질문에 넣는다.

**C. 양식 루틴 — 양식 확인·값 JSON 뼈대** (사진과 무관)
- 사진대지 양식을 정한다(입고·납품·설치 등. 이름이 여러 개면 사용자에게 확인).
- `hwpx` 스킬의 `pages <서식>` 으로 반복할 사진 페이지 번호, 페이지당 사진 칸 수(예: 2장), 공통 키(공사명·위치·날짜 등)를 확인한다.
- `photo_sheet_types.md` 로 종류별 필수 사진(예: 납품의 랙 전·후 전면·후면 4장, H/W·S/W 정상 실행)이 다 있는지 확인하고, 빠진 것을 질문에 넣는다.
- 공통 값 중 이미 아는 것은 채우고, 모르는 것은 확인 질문에 넣는다. 날짜를 촬영 시각으로 채우려면 그것도 질문에 넣는다.

**D. 관리동 위치 정리 — 제공 예정** (위 셋과 별개)
아직 없는 기능이다. 요청이 오면 "제공 예정" 이라고 안내하고, 지금은 A 의 방문 → 장소 표를 넘겨준다.
- 관리동이 등록돼 있지 않으면 등록
- 등록돼 있으면 위치 정보가 저장돼 있는지 확인하고, 사진 위치와 맞는지 검토해 수정 제안
- 비어 있는 주소·위도·경도 채우기

### 3. 질문 한 번에
A·B·C 에서 모은 질문을 한 메시지로 묻는다: 방문별 장소, 확인이 필요한 사진 설명·중복, 사진 순서(시각이 없을 때), 빈 공통 값, 방문이 바뀔 때 새 페이지에서 시작할지, 주소 변환 동의(필요할 때).
B 가 아직 끝나지 않았으면 A·C 질문을 먼저 묻고, B 결과는 도착하는 대로 이어서 확인한다.

### 4. 채우기
C 의 뼈대에 A 의 순서·장소와 B 의 설명을 넣어 값 JSON 을 완성하고, 넣기 전에 사진 순서·설명 목록을 보여 준 뒤 `hwpx` 스킬로 `fill`(hwpx) 또는 `export`(PDF)를 실행한다. 결과 요약(값 없음·경고)을 전한다.

## 주의
- **위치(GPS)는 민감 정보다.** 사용자가 요청하지 않으면 좌표를 사진대지·값 JSON 에 넣지 않는다. 사진대지의 `위치` 칸에는 사용자가 확인한 장소 이름을 쓴다.
- 장소·관리동 이름은 사용자가 답한 것만 쓴다. 좌표·주소만 보고 단정하지 않는다.
- 촬영 시각이 없는 사진의 날짜를 파일 이름으로 추측하지 않는다.
- 사진 순서·설명은 문서에 그대로 나가는 내용이다. 자동으로 정한 것은 넣기 전에 목록으로 보여 준다.
